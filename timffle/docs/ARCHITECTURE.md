# 架構與安全模型

這份文件說明各元件怎麼分工、一條 Socket 連線的完整流程，以及安全上的取捨。通訊協定的細節在 [`PROTOCOL.md`](PROTOCOL.md)。

## 1. 為什麼需要這些元件

- Flash 遊戲用 `flash.net.Socket` 直接連 TCP。瀏覽器網頁與 Chrome 擴充功能**都不能**開 TCP 連線，只能開 WebSocket。
- Ruffle 的網頁版對此的做法是：把 `Socket` 的連線轉成 **WebSocket 連到一個「代理」**，由代理再去連 TCP（設定項 `socketProxy`：`{ host, port, proxyUrl }`）。官方做法需要使用者自己架代理。
- 本專案的做法：**代理就是 Chrome 的 Native Messaging 小幫手**。擴充功能把 `socketProxy` 設成一個保留網址，頁面端攔下這個網址的 `WebSocket`，改走「內容腳本 → 背景服務 → Native Messaging → 小幫手 → TCP」。使用者不必架代理，也不必填網址。
- 另保留傳統做法作為進階選項：[`relay/`](../relay/) 是本機 WebSocket↔TCP 代理，擴充功能的「自訂 WebSocket 代理」模式把 `socketProxy` 指向它。

## 3. 一條連線的生命週期

1. 遊戲呼叫 `socket.connect(host, port)`。Ruffle 依 `socketProxy` 的萬用字元對應（`host:"*"`, `port:0`）得到代理網址 `ws://timffle-socket.invalid/connect?host={host}&port={port}`，建立 WebSocket。
2. 頁面端橋接認出這個網址（`.invalid` 是保留的頂級網域，永遠不會真的解析），驗證 `host`／`port` 參數的格式，向內容腳本要求開啟 Socket。
3. 內容腳本開一個專屬的 runtime Port 連到背景服務；背景服務從瀏覽器提供的 sender 取得頁框真正的來源，查「一律拒絕」「一律允許」清單與這個分頁這次造訪的回答：拒絕就回 `not_allowed`，允許就繼續，**兩者都沒有就先詢問使用者**（第 3a 節）。通過後檢查全域與每頁框的上限，然後啟動小幫手並先送 `hello` 協商協定版本（不相容或找不到就回報錯誤，選項頁會顯示原因）。
4. 小幫手收到 `open` 後解析 DNS、檢查位址、連 TCP；**TCP 連上之後**才回 `opened`。
5. 傳輸：每次最多送 64 KiB，且同時只有一個未確認的 `send`（小幫手整個寫完 TCP 才回 `sent`）；收到的資料每次最多 32 KiB，頁面確認（`ack`）之後小幫手才繼續讀。因此兩個方向的佇列都有上限，不會無限成長。
6. 任一端關閉、逾時（30 秒沒有進展）、頁面導覽或設定被撤銷時，整條鏈一起關閉，小幫手程序退出。

### 3a. 第一次連線的詢問

**誰會被問**：連線方式是「連線小幫手」、Socket 沒有被停用、來源是 `http(s)`，而且既不在「一律允許」也不在「一律拒絕」、這個分頁這次造訪也還沒回答過。`socketPermission()`（`socket-proxy.ts`）把一個來源判成 `allow`／`deny`／`ask`（沒有網站來源或 Socket 停用是 `off`，永遠不問）；「一律拒絕」優先於「一律允許」。「自訂 WebSocket 代理」模式不問：沒列出的網站直接拒絕。沒有 `nativeMessaging`（例如 Firefox 建置）的瀏覽器也不問——問了也連不上小幫手。

**兩種連線方式各有自己的「一律允許」清單**：`allowedOrigins` 是連線小幫手的清單（詢問視窗與彈出視窗的「允許」寫在這裡），`proxyOrigins` 是自訂代理的清單——只有這份清單裡的網站會拿到代理網址與 token。兩份分開，是為了讓「在小幫手模式按過允許的網站」不會因為使用者之後切到自訂代理，就悄悄拿到 token（審查發現的問題）。「一律拒絕」是共用的，兩種方式都優先。切換方式時設定頁換顯示該方式的清單；彈出視窗與詢問視窗只改目前方式的清單（「拒絕」例外，兩份都移除）。舊版（沒有 `proxyOrigins`）存的設定，兩種方式沿用同一份清單，行為與以前完全相同——包括預設清單的升級：從沒改過的舊預設清單（只有摩爾莊園）會跟著新預設，`allowedOrigins` 與 `proxyOrigins` 各自判斷（`upgradeLegacyDefaults`），使用者改過的清單不動。

**頁面端**：`ask` 的網站也會收到保留網址的 `socketProxy`（沒有任何機密），好讓第一次連線能走到背景服務的檢查；內容腳本照樣建立橋接通道，但把 port 以 `lazy` 標記交給頁面端 `ruffle.ts` 暫存，**直到 Ruffle 第一次讀 `config.socketProxy`（電影要載入之前）才安裝 `WebSocket` 轉接**（`socket-bridge-arm.ts`：在設定物件的 `socketProxy` 上放一個 getter，只觸發一次）。所以沒有 Flash 內容的網頁看到的仍是原生 `WebSocket`；已允許的網站維持原本的行為（立刻安裝）。

**背景端**（`socket-bridge-background.ts` 的 `evaluate`／`authorize`）：
1. 讀設定、玩家開關與這個分頁的「本次造訪」回答（`socket-visit.ts`，存在 `storage.session`，所以 service worker 重啟後還在、瀏覽器重啟後消失）。設定在讀取期間改變就重讀。
2. 結果是 `ask` 時呼叫 `socket-prompt.ts` 的詢問管理：同一個來源的要求（含不同分頁）共用一個項目，**同步建立**，所以同時開的多條 Socket 只問一次；一次只開一個視窗，其餘排隊（上限 8 個來源）；每個分頁每次造訪最多開 3 次視窗（算在最先發問的分頁上，超過就不問直接拒絕；已經用完 3 次的分頁再問新的來源，會當場被拒絕，不排隊、不佔等待中的 Socket 名額）；整個擴充功能每分鐘最多開 6 個詢問視窗，不論有幾個分頁在問（超過就不問直接拒絕，也不消耗分頁自己的 3 次）。**只有真的要開的視窗才算進這 6 個**：被分頁自己的 3 次上限拒絕的問題不算（複審重現過：用完額度的分頁一直問，曾經能把全體額度耗光，讓別的分頁的問題都被拒絕）。**等待回答的 Socket 不佔連線名額**：它們不算進全域 16 條／每頁框 8 條的上限，而是另有上限（每個分頁 4 條、全部 8 條，超過的立刻以 `socket_limit` 拒絕）——否則一個沒人理的問題會在 30 秒內一直佔住名額，讓已允許網站的 Socket 也連不上（審查重現過）。回答「允許」之後才開始佔名額；那時名額若已滿就回 `socket_limit`，不會讓它卡著。
3. 視窗用 `chrome.windows.create({ type: "popup" })` 開在發問分頁所在視窗的中央，網址帶一個隨機的問題 ID。視窗的文字與答案都經背景服務：只有**擴充功能自己的 `prompt.html`、最上層頁框、在這個問題的視窗裡**才能讀問題（`socket_prompt_get`）或回答（`socket_prompt_answer`）；網頁、其他頁面、被網頁嵌進頁框的 `prompt.html` 都被忽略。問題 ID 與視窗 ID 都要對。
4. 收到答案時，**先確認這個網站現在還是「該問」的**（模式可能已被切到自訂代理、Socket 可能被停用或它已被決定）：不是的話答案作廢，視窗顯示「已失效」；寫入設定時也在同一個交易裡再檢查一次。接著存起來，**背景服務再重新判斷一次**（而不是直接相信「按了允許」）：「一律」寫進 `storage.local` 的設定；「這次」記在這個分頁、這個網站的 `storage.session`，並在分頁關閉、或最上層頁面換到別的來源（`tabs.onUpdated`）時清除，重新整理同一頁不算。關掉視窗＝拒絕這次造訪。
5. 問題開著時，等待中的 Socket 連線以 30 秒（與頁面端的停滯逾時相同）為限，逾時回 `prompt_timeout`；Socket 先放棄（遊戲自己逾時）不會關掉視窗，之後的回答仍然算數。設定在別處被改成已決定的來源（選項頁、彈出視窗），或被切到自訂代理／停用 Socket 時，問題自動結束；玩家開關被關掉時，所有問題都結束。視窗在瀏覽器回報視窗 ID 之前就被關掉，也會被認出來（否則佇列會卡死）。

**詢問視窗的防護**：獨立視窗，網頁碰不到；預設選取並醒目標示的是「拒絕（建議）」；輸入要同時符合（`prompt-guard.ts`，有單元測試，也在真的視窗裡測）：視窗出現或取得焦點後 0.7 秒內忽略所有輸入，沒有焦點時完全不算；不接受腳本產生的點擊（`isTrusted`）；**按下**要發生在那 0.7 秒之後（按著鍵進來、之後才放開不算）；**「允許」只接受指標點擊，鍵盤永遠不能允許**（Tab、Enter、Space 是遊戲登入時最常打的鍵，視窗搶走焦點時不能因此被允許），而且滑鼠或觸控筆必須在那 0.7 秒之後在那顆按鈕上移動過（指標只是停在按鈕出現的位置不算；觸控螢幕沒有懸停，用點按）；「拒絕」任何輸入都可以，所以鍵盤使用者隨時能拒絕，要允許請用工具列彈出視窗裡的按鈕。**擴充功能自己的頁面不能被網頁嵌進頁框**：manifest 的 `web_accessible_resources` 只剩 `dist/*`（Ruffle 本身）與 `player.html`（SWF 連結被導向的獨立播放器），彈出視窗、設定頁、歡迎頁與詢問頁網頁完全載不進頁框（瀏覽器顯示錯誤頁；有端對端測試）；萬一被嵌入（例如瀏覽器行為不同），設定頁、詢問頁什麼都不顯示，彈出視窗的 Socket 區塊也不顯示。視窗開著期間用一個 runtime Port 每 10 秒送 ping，讓 MV3 service worker 不會因閒置被回收（回收會丟掉等待中的連線與問題；有對照實驗證明這個 Port 是必要的，見 [`TESTING.md`](TESTING.md)）。

**設定的寫入**（`proxy-settings.ts`）：彈出視窗、設定頁、詢問視窗（經背景服務）會同時改同一份設定。所有「讀取—修改—寫入」都在一個跨頁面共用的 Web Lock 裡進行，所以兩個同時的更新不會互相蓋掉；**設定頁的表單還要比對**：儲存時如果設定自從表單載入之後被別處改過（例如在彈出視窗把某網站設成「一律拒絕」），這次儲存會被拒絕、改為顯示最新設定——否則表單裡舊的清單會悄悄把「一律拒絕」改回「一律允許」。沒有編輯過的表單會自動跟著別處的變更更新；有編輯的表單會顯示警告但不被覆蓋。

**彈出視窗**（`popup-socket.ts`）：顯示目前分頁的網站（瀏覽器不告訴分頁網址時，只採用最上層頁框自己回報的來源，不採用「第一個回應的頁框」）；「允許此網站使用 Socket 連線」一鍵寫入目前方式的「一律允許」清單（自訂代理模式的按鈕會明講「會取得 token」）；存不了時（例如自訂代理模式下拿掉最後一個允許的網站）顯示原因，下拉選單還原；下拉選單切換「每次造訪時詢問」（兩個清單都移除）／「一律允許」／「一律拒絕」，並清除這個分頁這次造訪的回答（背景服務同時關掉依賴那個回答的連線）。這個分頁裡被詢問過的其他網站的頁框也會列出。非網站的分頁（`chrome://`、本機檔案、擴充功能頁面）不顯示這個區塊。

### 3b. 小幫手沒裝好時的提示，與「直接下載安裝程式」

Chrome 擴充功能不能自己執行程式，所以**沒有辦法由擴充功能代使用者執行安裝程式**；能做的是讓使用者看得到「少了什麼」，並**替他下載對的安裝檔**（執行那一下仍是使用者的）。四個地方：

- **彈出視窗的提示**（`popup-helper.ts`）：只有在**需要小幫手**時才去問——Timffle 開著、Socket 沒被停用、連線方式是「連線小幫手」、瀏覽器有 `connectNative`（Firefox 建置沒有）——才向背景服務問小幫手的狀態（`socket_helper_status`，和設定頁用的是同一個請求，背景服務共用同一個探測：啟動小幫手、只送 `hello`、馬上結束，不開任何 TCP）。答案是「找不到」或「版本不相容」才顯示提示與「直接下載安裝程式」按鈕；其餘（正常、逾時、啟動失敗、連線數已滿…）什麼都不顯示，免得誤報。探測在彈出視窗其餘內容載入的同時進行，提示在答案回來時才出現。**系統在提示出現之前就判斷好了**：按鈕下面一行寫著「適用於 Windows 64-bit」之類，後面接「其他系統與安裝說明」（開安裝頁）。按鈕只接受真的點擊（`isTrusted`），兩秒內重複的點擊算同一次；一點就開始下載，彈出視窗不關，提示的句子換成「已開始下載。下載完成後請執行安裝程式，再重新整理遊戲頁面。」。判斷不出系統（ChromeOS、Android、沒有處理器資訊的 Mac…）時沒有按鈕，只剩「其他系統與安裝說明」。彈出視窗被網頁嵌進頁框時什麼都不做。
- **設定頁**：「連線小幫手」狀態列旁，找不到或不相容時多一顆同樣的按鈕與同樣的一行說明；點了之後狀態列改成「已開始下載…」。狀態句子與彈出視窗、安裝頁共用 `helper-status.ts`；系統判斷與下載共用 `helper-download.ts`。
- **安裝頁**（`helper.html`／`helper.ts`，只能在擴充功能的分頁裡開；不在 `web_accessible_resources`，網頁嵌不進去）：為什麼需要小幫手、狀態列與「重新檢查」、Windows／macOS／Linux 各一組（這個系統的每個安裝檔的直接下載連結，**這台電腦的排在最前面並加框**；下面一行說怎麼執行，Linux 那行直接給出可以複製的指令）、「完全關閉 Chrome 再檢查」的提醒、安裝程式的保證（只替目前使用者安裝、不需要系統管理員權限、不裝背景服務、不改安全設定）、以及到該版本 Releases 頁面的連結。頁面開著時，分頁回到前景會自動再檢查一次。只有 `/options.html`、`/popup.html`、`/helper.html` 的最上層頁框問得到小幫手狀態；網頁、其他擴充功能頁面、頁框內的頁面都問不到。
- **工具列圖示的紅色「!」**：某個頁面的 Socket 因為 `helper_missing` 或 `helper_incompatible` 失敗時，背景服務對**那個分頁**設 `action.setBadgeText({tabId, text: "!"})`（紅底）。徽章是分頁專屬的，分頁換到別的頁面就消失（在 Chrome 155 實測過）；沒有 `action` API 的瀏覽器或已不存在的分頁都靜默略過。其他種失敗（伺服器拒絕、被允許清單擋下…）不設徽章。

**怎麼判斷系統**（`helper-download.ts` 的 `chooseInstaller`）：用 `navigator.userAgentData.getHighEntropyValues(["architecture", "bitness", "platform"])`——作業系統名稱加上**處理器**（`x86` 或 `arm`，與 32／64 位元）。Windows：x86＋64 → x64、x86＋32 → x86、arm＋64 → ARM64（arm＋32 沒有安裝檔）；macOS：arm → Apple 晶片、x86 → Intel（**只看處理器，不看 User-Agent**：Apple 晶片的 Mac 上 Chrome 的 User-Agent 也寫 Intel；沒有處理器資訊就不猜，猜錯的程式根本開不起來）；Linux：x86＋64 → x64、arm＋64 → ARM64。Chrome OS 與 Android 沒有安裝檔。沒有 `userAgentData` 的瀏覽器退回讀 User-Agent（Windows 的 `Win64`／`WOW64`／`ARM64`、Linux 的 `x86_64`／`aarch64`），讀不出來的就是沒有。判斷結果以真的 Chrome 用 `Emulation.setUserAgentOverride` 模擬每一種系統測過（`browser-auto-tests.mjs`）。

**怎麼下載**：`tabs.create({ url, active: false })` 開一個背景分頁到檔案的位址；GitHub 把 release 的檔案當成附件（`Content-Disposition: attachment`）回應，Chrome 就存檔、顯示它自己的下載提示，並**自己關掉那個分頁**（在 Chrome 155 實測）。所以不需要 `downloads` 權限，也不用在擴充功能裡把檔案抓進記憶體；彈出視窗中途被關掉也不影響（下載是瀏覽器的事）。代價：**沒有事先檢查**——檔案不存在（還沒發佈、倉庫是私人的）時，那個分頁會停在 GitHub 的「找不到頁面」，沒有檔案被存下來，提示仍然寫「已開始下載」；這個情形有測試記錄（`popup-release-not-found-saves-nothing-and-shows-githubs-page`）。

**下載位置**：GitHub 倉庫 `Im-Tim-mI/Timffle-Helper`，**只放安裝檔**（release 檔案，不放原始碼）。插件釘在**一個**release 標籤（`helper-download.ts` 的 `HELPER_RELEASE`，等於小幫手的版本 `v1.3.0`；單元測試比對 `timffle/helper/main.go` 的 `version`），不是「最新版」：之後出了通訊協定不同的小幫手，舊插件仍然下載它對應的那一份，不會裝到它用不了的小幫手。檔名、格式、怎麼做出來、怎麼發佈新版：見 [`HELPER-DOWNLOADS.md`](HELPER-DOWNLOADS.md)。

沒有新權限（不需要 `downloads`、`notifications`）；插件**不抓取、不檢查、不解壓縮、不執行**下載的檔案，只是請瀏覽器下載它，之後執行與否是使用者的事。安裝頁與提示的文字與其他頁面一樣放在 `timffle/locales/`，36 種語言都有。

## 4. 安全模型

### 保護的目標

- **不讓任意網站使用 Socket**：只有使用者答應過的網站可以——「一律允許」清單內的網站（預設是淘米的四個遊戲網站），或使用者在詢問視窗按「允許」的那個分頁這次造訪；內嵌播放器以所在頁框的來源判斷，獨立播放器以 SWF 網址的來源判斷，**本機檔案永遠不能用**。清單只接受完整的 `http(s)` 來源（協定＋主機＋選用連接埠），不接受萬用字元、路徑、帳密、查詢；「一律拒絕」優先於「一律允許」。
- **詢問不能被網頁冒用或點穿**：問題在擴充功能自己的視窗裡問（網頁無法覆蓋、無法替使用者按）；來源是背景服務從瀏覽器提供的 sender 取得的，不是頁面傳來的字串；回答只接受來自那個視窗的訊息；網頁根本載不進這些頁面（見上）；輸入防護見第 3a 節。一個網頁最多讓一個分頁每次造訪開 3 個視窗，整個擴充功能每分鐘最多 6 個，同時最多 8 個來源排隊。
- **自訂代理的 token 只給它自己清單裡的網站**：與小幫手的「允許」清單分開（見第 3a 節）。
- **不讓其他擴充功能或程式叫用小幫手**：Chrome 只允許 Native Messaging 主機清單的 `allowed_origins` 內的擴充功能啟動它；小幫手自己還會檢查 Chrome 傳入的第一個引數必須剛好是 `chrome-extension://eandddnbchclalbjkhfelhjhpijifcog/`（Windows 另可多一個 `--parent-window=<數字>`）。
- **不讓小幫手變成打進內網的跳板**：只連**公開位址**。DNS 解析的結果只要有任何一個不是公開位址就整批拒絕，通過後釘住該位址連線（避免 DNS rebinding）；封鎖 IPv4 的私網、迴路、連結本地、CGNAT、文件／測試／保留／多播區段，IPv6 只允許 `2000::/3` 並排除 Teredo、6to4、文件、基準測試、ORCHID 等特殊用途區段；IPv4 對映的 IPv6 位址套用 IPv4 規則。
- **正式版沒有任何可以放寬位址限制的開關**：允許私網位址的行為只存在於以 `-tags localtest` 編譯的測試版（自動化測試要連 localhost 用），`helper/build.sh` 明確以空的 tags 編譯，並拒絕環境裡殘留的 `GOFLAGS`。頁面訊息無法要求放寬。
- **資源上限**：全域 16 條、每頁框 8 條、單次送出 ≤ 64 KiB、單次接收 ≤ 32 KiB、緩衝 ≤ 1 MiB、佇列 ≤ 1024 筆、停滯 30 秒逾時、連線預設 20 秒（可設 1～120 秒）。
- **隱私**：小幫手不記錄連線內容或帳密；沒有任何程式碼把資料送往本專案以外的地方。

### 安裝程式

- 只做每個使用者的安裝，不需要系統管理員，不裝系統服務，不開機自動啟動。
- 不自動移除下載標記（Windows 的 Mark of the Web、macOS 的 quarantine），也不停用任何系統安全功能。
- 寫檔用暫存檔加改名（盡量原子）；拒絕符號連結與 Windows reparse point；遇到內容不符的既有檔案或外來登錄項目就不覆寫。
- 安裝收據（`install.json`）綁定原生檔案的雜湊；移除時只刪收據列出且雜湊相符的檔案，Windows 登錄只清除本元件的預設值。
- 註冊的瀏覽器：Google Chrome 正式版一律註冊。Windows 上 Chrome 各頻道共用同一個登錄 key；Linux／macOS 的 Beta、Dev、Canary 與 Chromium 只在使用者目錄裡已有該瀏覽器的資料夾（用過）時才註冊。Edge、Brave 等其他瀏覽器不註冊。

### 仍然存在的風險（請誠實看待）

1. **被允許的網站可以透過小幫手連到公開網路上的任何 TCP 位址**——這正是 Socket 功能本身。所以只允許你信任的網站。若那個網站被入侵，攻擊者可以把你的電腦當成連到公開網路的 TCP 出口（但到不了你的內網）。詢問視窗把「拒絕」放在預設位置並警告「只有線上遊戲可以允許」，但**使用者仍可能按錯或被說服去按允許**——這一步的把關最終在人，不在程式。
2. **擴充功能 ID 來自公開的公鑰。** 任何人把同一把公鑰放進自己擴充功能的 `manifest.json`，載入後就是同一個 ID，也就能叫用你電腦上的小幫手。這是「發行未封裝擴充功能」的固有限制；因此只載入來自可信來源的擴充功能。要自行散布請換成自己的金鑰（見 [`BUILD.md`](BUILD.md#4-使用自己的擴充功能金鑰)）。
3. **小幫手沒有 Microsoft／Apple 簽章或公證。** Windows 的 Smart App Control 等政策可能直接擋下；請不要為此停用系統保護。發行 ZIP 附 SHA-256，請核對。
4. **依賴瀏覽器行為**：Native Messaging、MV3 service worker 的生命週期（自訂代理模式另有 Local Network Access 權限）會隨 Chrome 版本變動，目前只在 Chrome 155 驗證過。

5. **詢問機制的已知限制**（獨立審查找到、刻意不處理或只能降低的）：
   - 來源是精確比對，`http`／`https`、有無 `www.`、不同連接埠都是不同的網站，各自被問、各自被拒絕。惡意頁面可以用很多個網域各問一次，但被每個分頁每次造訪 3 次、全體每分鐘 6 次的上限擋住。
   - 同一個分頁裡的惡意頁框，可以把該分頁每次造訪的 3 次額度用掉，讓同一頁其他網站不再被問；使用者仍可在彈出視窗一鍵設定。
   - 一個沒人回答的視窗，會讓排在後面的其他網站的問題等著（一次只問一個）；等待中的 Socket 30 秒後逾時，視窗不會自己消失。
   - 沒有 `storage.session` 的舊瀏覽器（Firefox 115 以前），「這次造訪」的回答只活到 service worker 被回收；視窗開著時 service worker 若真的被重啟，舊視窗按下去才會顯示「已失效」。
   - 網頁含有同源的 `iframe` 時，Ruffle 自己的頁框偵測會讀取設定（`config.socketProxy`），於是「只被問」的網站也會提早安裝 `WebSocket` 轉接；它對一般的 WebSocket 連線行為與原生相同。

## 5. 設定與模式

設定存在擴充功能的 `storage.local`（不使用同步儲存）：

| 設定 | 說明 |
|---|---|
| `mode` | `helper`（預設）或 `websocket`（自訂代理）。舊版沒有 `mode` 的設定：有代理網址的視為 `websocket`（行為不變），沒有的視為 `helper` |
| `allowedOrigins` | 連線小幫手的「一律允許」網站來源清單（預設是淘米四站） |
| `proxyOrigins` | 自訂 WebSocket 代理的「一律允許」清單，只有這裡的網站拿得到代理網址與 token（預設同樣是淘米四站）。這個欄位出現之前存的設定沒有它，兩種方式沿用同一份 `allowedOrigins`；之後兩份各自演變 |
| `deniedOrigins` | 「一律拒絕」的網站來源清單。這個欄位出現之前存的設定沒有它，視為空；同一個來源兩邊都有時拒絕優先 |
| `defaultsVersion` | 預設清單的版本。版本升級時，若使用者儲存的清單恰好等於舊預設值，就換成新預設；使用者自訂過的清單不動。`allowedOrigins` 與 `proxyOrigins` 各自判斷 |
| 代理網址樣板 | 只用於 `websocket` 模式，必須含 `{host}`、`{port}`，不得含帳密或片段 |

`helper` 模式下，擴充功能在允許的網站與「會被詢問」的網站上把 Ruffle 的 `socketProxy` 設成 `[{ host: "*", port: 0, proxyUrl: <保留網址樣板> }]`（保留網址沒有任何機密）；「一律拒絕」的網站與本機檔案**完全收不到**這項設定，也不會有任何對外連線。`websocket` 模式下，代理網址（含 token）只給 `proxyOrigins` 裡的網站，不在清單的網站什麼都收不到。

另外，「這次造訪」的回答存在 `storage.session`（鍵 `socketVisit:<分頁 ID>`，只有背景服務與擴充功能頁面讀得到，內容腳本與網頁讀不到）。

## 6. 為什麼是「每個 Socket 一個程序」

- 簡單：沒有多工、沒有程序間狀態，小幫手一個程序只管一條 TCP；Chrome 關掉 Port 或擴充功能 service worker 被回收，stdin EOF 就讓小幫手關閉 TCP 並退出，不會留下常駐程序。
- 安全：沒有可供他人連入的連接埠；也沒有一個長期存在的程序累積狀態。
- 代價：每條連線啟動一個程序；Windows 上啟動程序的成本比 Linux 高。我們沒有量測這個開銷，也沒有在 Windows 實機上確認過。

## 7. 介面語言

擴充功能的頁面（設定頁、彈出視窗、詢問視窗）用 Chrome 的訊息目錄（`_locales/<語言>/messages.json`），語言跟著瀏覽器的介面語言，做法和 Ruffle 相同，支援同樣的 36 種語言。

- **文字放哪裡**：Timffle 自己新增的文字，鍵都以 `timffle_` 開頭，來源在 [`../locales/`](../locales/)（每種語言一個檔案；英文是完整來源，帶給翻譯者的說明與佔位符）。`scripts/sync_locales.py` 把它們複製進 `web/packages/extension/assets/_locales/*/messages.json`；`--check` 確認複製結果是最新的，並檢查每種語言都有每一句，佔位符（`$VERSION$`）、使用者要照打的 `{host}`／`{port}` 與 `<1>…</1>` 標記沒有被翻譯弄丟。為什麼不直接改那些檔案：跟進上游時 `messages.json` 一律取上游版本（Crowdin 會更新它們），分開存放才不會被蓋掉。`rebrand.py` 不碰 `timffle_` 開頭的訊息（它們刻意提到 Ruffle）。
- **頁面怎麼取字**：HTML 裡不放這些文字，只標 `data-i18n="鍵"`，`i18n.ts` 的 `localizePage()` 在頁面載入時填入。含連結或粗體的句子用 `data-i18n-rich`，句子裡的 `<1>…</1>` 對應到該元素的第 1 個子元素（連結的位址留在 HTML 裡，不進翻譯）；用程式組出來的文字（狀態、錯誤、按鈕）用 `text("鍵")`。找不到的鍵會直接顯示鍵名，不會留白，單元測試確認程式與頁面用到的鍵都存在、目錄裡沒有沒人用的鍵。
- **方向與語言屬性**：`setPageLanguage()` 設定 `<html lang>` 與 `dir`（阿拉伯文、希伯來文是 `rtl`，取自 Chrome 的 `@@bidi_dir`）。網址、來源清單這類資料固定由左到右（`dir="ltr"`）；阿拉伯文與希伯來文裡的 `ws://`、`wss://` 後面放了一個由左到右標記（U+200E），否則 `://` 會被排成反的。
- **機器翻譯**：英文與繁體中文由作者撰寫，其他 34 種是機器翻譯，沒有母語人士審閱；README 的「語言」段落與 [`../locales/README.md`](../locales/README.md) 照實說明。
- **Chrome 的限制**：Chrome 沒有波士尼亞文、世界語、加利西亞文與韃靼文的介面語言，這四種在 Chrome 上顯示英文（翻譯仍附上，和 Ruffle 一樣）。
- **折扣碼區塊**（0.8.0.26302）：設定頁與彈出視窗裡有一個羅技（Logitech）台灣官方線上商城的九折優惠碼區塊（`timffle_promo_*`，連結 `https://store.logitech.tw/discount/LOGITIM`；Shopify 的折扣連結，點開會把 `LOGITIM` 放進購物車的 cookie）。**只在瀏覽器介面是英文或中文時顯示**（這是台灣商店的折扣碼，不需要每種語言都有）：區塊在 HTML 裡預設 `hidden`，並標 `data-i18n-languages="en zh"`，`localizePage()` 取 `browser.i18n.getUILanguage()` 的第一段（`en-GB` → `en`、`zh-TW` → `zh`）比對，符合才取消隱藏。所以只有 `en`、`zh_TW`、`zh_CN` 三個目錄有這六句文字，其他語言連文字都沒有（`sync_locales.py` 與單元測試強制：其他語言帶有這些鍵會失敗）。純靜態 HTML：沒有任何程式碼會連到那個網站，橫幅圖放在擴充功能裡（`images/promo-logitech-zh.png`／`-en.png`，由訊息 `timffle_promo_image` 決定，中文用中文橫幅、英文用英文橫幅），頁面不從網路載入任何東西，只有使用者點連結才會開新分頁（`rel="noopener noreferrer"`）。彈出視窗裡是 `<details open>`（摘要 `timffle_promo_summary`，使用者可以按摘要折疊）：**預設展開**，所以彈出視窗比 Chrome 的 600 px 上限高，超出的部分用捲動看（`popup.css` 的 `body` 可垂直捲動；橫幅、連結與「與羅技毫無關係」的聲明在摺線之下）；折疊後只剩一行，整個彈出視窗回到 600 px 以內。單元測試與瀏覽器測試都檢查連結網址一字不差、英文與中文的橫幅與聲明都有、其他每種語言都看不到、英文與中文的彈出視窗在區塊之上的控制項加上摘要那一行放得進 600 px、展開的區塊可以捲到最底而且沒有橫向溢出、折疊後整個彈出視窗不超過 600 px。程式碼（`src/`）不得提到這個網站。
- **沒涵蓋**：連線小幫手安裝程式的訊息（繁體中文＋英文雙語）、獨立播放器頁（`player.html`，Ruffle 原本就沒有翻譯）。
